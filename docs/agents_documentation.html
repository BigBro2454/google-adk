hello_world

Your first ADK agent. A math assistant with calculator tools. Demonstrates the core tool-calling loop and FallbackLlm.

agents/hello_world/agent.py FallbackLlm add · subtract · multiply

Execution workflow

User sends a math question → ADK passes it to Gemini with the system instruction → Gemini decides which tool to call → ADK executes the Python function → the result is injected back into context → Gemini formats a friendly reply.

Step 1 Agent definition agent.py

Step 2 Tool functions — type hints + docstrings are load-bearing tools/calculator.py 
def add(a: float, b: float) -> dict:
    """Adds two numbers together.

    Args:
        a: The first number.
        b: The second number.
    Returns:
        A dict with the sum result.
    """
    return {"result": a + b}

def subtract(a: float, b: float) -> dict:
    """Subtracts two numbers."""
    return {"result": a - b}

def multiply(a: float, b: float) -> dict:
    """Multiplies two numbers together."""
    return {"result": a * b}
Type hints (float, dict) are mandatory. ADK uses them to build the JSON schema passed to the LLM — without them, tool calling breaks silently.
Docstrings are the tool's contract with the LLM. Quality directly determines how reliably the LLM calls the tool and with what arguments.
Return a dict — ADK serializes it to JSON and feeds it back to the LLM so Gemini can reason about the result.

Bug caught during Week 2: Model was initially gemini-3.1-flash-lite (does not exist). Fixed to gemini-2.0-flash. Always verify model names — invalid names fail silently with a confusing error.

Step 1 Agent — enforcing tool order via instruction text agent.py 
root_agent = Agent(
    name="weather_agent",
    model="gemini-2.0-flash",

    Step 1 - Always call get_coordinates

Tool order via instruction — “Step 1… Step 2…” in the system prompt is all you need for sequential execution. The LLM is the orchestrator.

Error handling in instruction — “apologise and ask to double-check” handles the case where the tool returns an error key instead of coordinates.
Step 2 get_coordinates — geocoding via Open-Meteo (no key) tools/weather.py 
def get_coordinates(city: str) -> dict:
    """Gets lat/lon for a city name.

    Always call this FIRST before
    calling get_weather.

    Args:
        city: City name (e.g. "Mumbai").
    Returns:
        Dict with latitude, longitude,
        name, country. Or 'error' key.
    """
    encoded = urllib.parse.quote(city)
    url = (
        f"https://geocoding-api"
        f".open-meteo.com/v1/search"
        f"?name={encoded}&count=1"
    )
    with urllib.request.urlopen(url) as r:
        data = json.loads(r.read())
    if not data.get("results"):
        return {"error": f"'{city}' not found"}
    result = data["results"][0]
    return {
        "latitude": result["latitude"],
        "longitude": result["longitude"],
        "name": result["name"],
        "country": result.get("country"),
    }
No extra libraries — uses Python's built-in urllib only. Zero extra dependencies beyond ADK itself.
Error key pattern — returning {"error": "..."} instead of raising lets the LLM receive the failure and handle it gracefully.
Docstring carries usage contract — “Always call this FIRST before calling get_weather” is in the docstring so the tool enforces its own ordering rule.
Step 3 get_weather — WMO codes to human-readable conditions tools/weather.py 
# WMO Weather Condition Codes
WMO_CODES = {
    0: "Clear sky",
    2: "Partly cloudy",
    3: "Overcast",
    63: "Moderate rain",
    95: "Thunderstorm",
    # ... 20+ more WMO codes
}

def get_weather(latitude: float,
               longitude: float) -> dict:
    url = (
        f"https://api.open-meteo.com"
        f"/v1/forecast"
        f"?latitude={latitude}"
        f"&longitude={longitude}"
        f"&current_weather=true"
    )
    with urllib.request.urlopen(url) as r:
        data = json.loads(r.read())
    current = data["current_weather"]
    wmo = int(current["weathercode"])
    return {
        "temperature_celsius": current["temperature"],
        "wind_speed_kmh": current["windspeed"],
        "weather_condition": WMO_CODES.get(wmo),
        "is_day": bool(current["is_day"]),
    }
WMO_CODES dict translates numeric codes (like 63) from the API into readable strings. The LLM gets "Moderate rain", not 63.
Descriptive return keys — temperature_celsius, weather_condition, is_day let the LLM describe weather precisely without guessing units.

github_agent

Access any GitHub repo, file, issue, or commit using MCP instead of hand-writing each tool function.

agents/github_agent/agent.py McpToolset github-mcp-server

Execution workflow

ADK spawns the GitHub MCP server as a subprocess on startup, communicating over stdin/stdout. At query time, Gemini selects a GitHub tool from the filtered list, the MCP server calls the real GitHub REST API, and the result flows back through ADK into the LLM context.

sequenceDiagram participant U as User participant ADK as ADK Runner participant G as "Gemini 2.5 Flash" participant MCP as "github-mcp-server (subprocess)" participant GH as GitHub REST API U->>ADK: "List open issues on my google-adk repo" ADK->>MCP: spawn process (stdio) + inject GITHUB_TOKEN ADK->>G: system prompt + filtered tool schemas (6 tools) G->>ADK: tool_call: list_issues(owner="BigBro2454", repo="google-adk") ADK->>MCP: JSON-RPC call over stdin MCP->>GH: GET /repos/BigBro2454/google-adk/issues GH-->>MCP: [{title, number, state, ...}] MCP-->>ADK: JSON-RPC response over stdout ADK->>G: tool result injected G-->>ADK: formatted issue list ADK-->>U: final reply

The key insight: MCP vs hand-written tools

Instead of writing def search_repos(...), def list_issues(...) etc., one McpToolset connects to the GitHub MCP server binary and imports all its tools automatically. One line of code gives you an entire platform's APIs.

💡

MCP (Model Context Protocol) is an open standard for exposing tools to LLMs. Any platform with an MCP server — GitHub, Slack, Notion, Postgres — plugs into any ADK agent with the same pattern.

Code walkthrough

Step 1 McpToolset — spawns the MCP server as a subprocess agent.py 
from google.adk.tools.mcp_tool.mcp_toolset import (
    McpToolset, StdioServerParameters
)

load_dotenv()
github_token = os.getenv(
    "GITHUB_PERSONAL_ACCESS_TOKEN"
)

github_toolset = McpToolset(
    connection_params=StdioServerParameters(
        command="github-mcp-server",
        args=["stdio"],
        env={
          "GITHUB_PERSONAL_ACCESS_TOKEN":
          github_token
        },
    ),
    tool_filter=[
        "search_repositories",
        "get_file_contents",
        "list_issues",
        "get_issue",
        "search_code",
        "list_commits",
    ],
)
StdioServerParameters — ADK launches github-mcp-server stdio as a subprocess and communicates over stdin/stdout. No HTTP server or port needed.
env injection — the token goes into the MCP server subprocess's environment, never into the LLM context. Secrets stay out of the prompt.
tool_filter whitelist — without it the agent gets all 30+ GitHub MCP tools, wasting context tokens and confusing the LLM. Expose only what you need.
Step 2 Agent definition — a toolset as a single tools entry agent.py 
root_agent = Agent(
    name="github_agent",
    model="gemini-2.5-flash",
    instruction="""

    search for user:BigBro2454.

    (e.g. BigBro2454/google-adk).

    """,
    tools=[github_toolset],  # whole MCP server
)
tools=[github_toolset] — a single McpToolset expands to all 6 filtered tools at runtime. ADK handles the expansion transparently.
Instruction shapes query format — “search for user:BigBro2454” makes the LLM produce correct GitHub search syntax automatically.

ollama_agent

100% offline. Swapping one string is all it takes to switch from Gemini to any local model.

ADK's LiteLlm adapter translates ADK's internal LlmRequest format into the OpenAI-compatible API that Ollama speaks. All inference runs on-device — no data ever leaves the machine.

from google.adk.models.lite_llm import LiteLlm
from agents.hello_world.tools.calculator import (
    add, subtract, multiply

# Change this one line to switch models
MODEL = "ollama_chat/qwen2.5:7b"
# MODEL = "ollama_chat/llama3.1:8b"
# MODEL = "ollama_chat/qwen3.5:9b"
# MODEL = "ollama_chat/qwen2.5-coder:7b"

os.environ["OLLAMA_API_BASE"] = "http://localhost:11434"

LiteLlm(model=MODEL) — the only difference vs a Gemini agent. Tools, instruction, sessions — everything else works identically.

OLLAMA_API_BASE — tells LiteLLM where Ollama is. Set via env var so the model URL is not hardcoded into the class.
Reuses hello_world tools — imports calculator functions directly from another agent's package. Tools can be shared freely across agents.
💡

Models installed on your machine: qwen2.5:7b (best tool-calling) · llama3.1:8b (general) · qwen2.5-coder:7b (coding) · qwen3.5:9b (most capable) · gemma4:12b (Google's own, locally)

dota_draft_analyzer

LLM-only agent with zero tools. All intelligence comes from a densely structured system prompt.

agents/dota_draft_analyzer/agent.py prompt engineering tools=[]

Execution workflow

No tool calls. No API calls. The entire execution is a single round-trip: user provides heroes → Gemini applies the structured INSTRUCTIONS prompt → structured 12-section analysis is returned immediately.

sequenceDiagram participant U as User participant ADK as ADK Runner participant G as "Gemini 2.5 Flash (FallbackLlm)" participant OL as "Ollama (fallback only)" U->>ADK: "I am playing Axe. Heroes: Axe CM DP vs PA Tide Puck" ADK->>G: INSTRUCTIONS system prompt + hero list Note over G: All reasoning in LLM weights. No tools, no API calls. G-->>ADK: 12-section pre-match analysis ADK-->>U: Strategy, Laning, Skill Build, Items, Timings... Note over G,OL: If rate-limited, FallbackLlm retries via Ollama silently

The pattern: structured prompt as the product

This agent has tools=[]. It shows that when domain knowledge is the differentiator, not API access, the prompt itself is the feature. The INSTRUCTIONS constant enforces a strict 12-section output the LLM must produce every time.

Code walkthrough

Prompt INSTRUCTIONS — output schema enforced in natural language agent.py 
INSTRUCTIONS = """
You are a high-level Dota 2 Coach.

CRITICAL RULES:
1. Exactly one bullet point per section.
2. Keep it punchy - readable before horn.
3. GUARDIAN MENTALITY: Write knowing
   all players tunnel-vision on kills
   and fail to coordinate combos.
   Frame all advice around exploiting
   this chaos and surviving your own
   team's mistakes.

Include exactly these sections:
* Strategy
* Laning Behavior
* Skill Build
* Item Progression
  * Laning (0-10m)
  * Mid Game (10-25m)
  * Late Game (25m+)
* Timings
* Threats
* Fighting Rules
* Map Focus
* Damage Distribution
* Metrics Targets
* Win Condition
* Solo Carry Backup Plan
"""
Module-level constant — separates the long prompt from the Agent(...) call. Keeps agent definition clean; the prompt is its own thing to edit.
“CRITICAL RULES” in all-caps — a known prompting pattern. All-caps headers receive more attention from the LLM, enforcing non-negotiable constraints.
Domain context baked in — “GUARDIAN MENTALITY” encodes the specific player profile (low-skill bracket, chaotic play). Makes output actionable vs generic.
12 mandatory sections — constraining the output schema makes responses consistent and scannable. Crucial when the user has 30 seconds before a match starts.

note_taking_agent

Stateful personal notes that persist across conversation turns. Introduces session.state and ToolContext injection — ADK's dependency-injection pattern for stateful tools.

agents/note_taking_agent/agent.py session.state ToolContext add · get · list · delete · clear

Execution workflow

Every tool function receives a ToolContext object injected by ADK. Tools read and write to tool_context.state["notes"] — a dict that survives for the entire conversation. No database, no files — just an in-memory session dict wired through ADK's state machinery.

sequenceDiagram participant U as User participant ADK as ADK Runner participant G as "Gemini 2.5 Flash (FallbackLlm)" participant T as notes tools participant S as session.state U->>ADK: "Save a note called 'ideas' about ADK patterns" ADK->>G: system prompt + user message G->>ADK: tool_call: add_note(title="ideas", content="ADK patterns") ADK->>T: add_note(title, content, tool_context=injected) T->>S: state["notes"]["ideas"] = "ADK patterns" S-->>T: write confirmed T-->>ADK: {"message": "Saved note 'ideas'. You now have 1 note(s)."} ADK->>G: tool result injected G-->>ADK: "Done! Saved your note 'ideas'." ADK-->>U: confirmation U->>ADK: "What notes do I have?" ADK->>G: user message (session.state persists) G->>ADK: tool_call: list_notes() ADK->>T: list_notes(tool_context=injected) T->>S: reads state["notes"] S-->>T: {"ideas": "ADK patterns"} T-->>ADK: {"count": 1, "notes": [{title, preview}]} ADK->>G: tool result injected G-->>ADK: "You have 1 note: 'ideas' - ADK patterns" ADK-->>U: note list

The key concept: ToolContext injection

ADK automatically injects ToolContext when it detects a parameter named tool_context in the function signature. The LLM never sees this parameter — it only sees title and content in the tool's JSON schema. This is ADK's dependency injection pattern for stateful tools.

💡

State scope: Keys without a prefix (state["notes"]) are session-scoped — they live for the current conversation only. Prefix with "user:" for user-scoped state that persists across sessions, or "app:" for app-scoped state shared by all users.

Code walkthrough

Step 1 Agent definition — FallbackLlm + 5 state-aware tools agent.py 
from google.adk.agents import Agent
from shared.utils.fallback_model import FallbackLlm
from .tools.notes import (
    add_note, get_note, list_notes,
    delete_note, clear_all_notes
)

root_agent = Agent(
    name="note_taking_agent",
    model=FallbackLlm(
        primary="gemini-2.5-flash",
        fallback="ollama_chat/qwen2.5:7b",
    ),
    description="A personal note-taking assistant...",
    instruction="""
    You are a helpful personal note-taking
    assistant. Map user intent to tools:

    Save / add / create  -> add_note(title, content)
    Read / show / get    -> get_note(title)
    List / show all      -> list_notes()
    Delete / remove      -> delete_note(title)
    Clear / delete all   -> clear_all_notes()

    tools=[add_note, get_note, list_notes,

)
Intent mapping in instruction — the explicit “Save → add_note” mapping removes ambiguity. The LLM does not have to infer which tool handles “jot down” vs “remember” vs “save”.
gemini-2.5-flash — upgraded from 2.0-flash. Better instruction following leads to more reliable tool selection across all five note operations.
FallbackLlm — same pattern as hello_world. Gemini first; if rate-limited, silently falls back to local Ollama without losing the session state.
Step 2 add_note — ToolContext injection pattern tools/notes.py 
from google.adk.tools import ToolContext

def add_note(
    title: str,
    content: str,
    tool_context: ToolContext  # injected by ADK
) -> dict:
    """Saves a new note (or updates an existing
    one) with the given title and content.

    Args:
        title: A short label for the note.
        content: The full text of the note.
        tool_context: Injected by ADK -
            provides access to session state.
    Returns:
        A dict with 'message' confirming save.
    """
    notes: dict = dict(
        tool_context.state.get("notes", {})
    )
    action = "Updated" if title in notes else "Saved"
    notes[title] = content
    tool_context.state["notes"] = notes
    return {
        "message": f"{action} note '{title}'."
                    f" You now have {len(notes)} note(s)."
    }
ToolContext parameter — ADK detects this by parameter name at registration time. It injects the live session context automatically; the LLM never passes it.
dict(state.get(...)) — creates a copy before mutating. ADK's state is a proxy; you must reassign to trigger a write: state["notes"] = notes.
Upsert pattern — checks if title exists first to report “Updated” vs “Saved”. Useful feedback for the LLM to include in its confirmation message.
Step 3 Remaining tools — get, list, delete, clear tools/notes.py 
def get_note(title: str, tool_context: ToolContext) -> dict:
    notes = tool_context.state.get("notes", {})
    if title not in notes:
        return {
            "error": f"No note '{title}' found.",
            "available_notes": list(notes.keys()),
        }
    return {"title": title, "content": notes[title]}


def list_notes(tool_context: ToolContext) -> dict:
    notes = tool_context.state.get("notes", {})
    if not notes:
        return {"count": 0, "notes": [],
                "message": "No notes yet."}
    previews = [
        {"title": t,
         "preview": c[:80] + ("..." if len(c) > 80 else "")}
        for t, c in notes.items()
    ]
    return {"count": len(notes), "notes": previews}


def delete_note(title: str, tool_context: ToolContext) -> dict:
    notes = dict(tool_context.state.get("notes", {}))
    if title not in notes:
        return {"error": f"No note '{title}' found.",
                "available_notes": list(notes.keys())}
    del notes[title]
    tool_context.state["notes"] = notes
    return {"message": f"Deleted '{title}'. {len(notes)} left."}


def clear_all_notes(tool_context: ToolContext) -> dict:
    """Deletes ALL notes. Only call if user
    explicitly asks to clear everything."""
    count = len(tool_context.state.get("notes", {}))
    tool_context.state["notes"] = {}
    return {"message": f"Cleared all {count} note(s)."}
available_notes in error — when a title is not found, returning all known titles gives the LLM the information to ask “did you mean X?” instead of a dead-end error.
80-char preview — list_notes returns truncated previews, not full content. Keeps tool responses small so they do not overflow the context window in long sessions.
Docstring guard on clear_all — “Only call if user explicitly asks” in the docstring prevents the LLM from nuking all notes on vague requests like “clean up”.

coordinator & worker (A2A System)

A multi-agent architecture utilizing the Agent-to-Agent (A2A) protocol. The coordinator delegates tasks to a remote worker acting as a sub-agent.

agents/coordinator/agent.py agents/worker/agent.json RemoteA2aAgent

Execution workflow

The coordinator agent acts as the main entry point for the user. When a task requires background work, it delegates the instruction over HTTP using the standard A2A protocol (JSON-RPC + SSE) to the worker agent, which is running as a separate service.

sequenceDiagram participant U as User participant ADK as Coordinator (ADK) participant W as Worker (A2A Endpoint) U->>ADK: "Can you analyze this background data?" ADK->>ADK: Coordinator decides to delegate to worker ADK->>W: JSON-RPC over HTTP (A2A Protocol) W-->>ADK: Streamed response (SSE) ADK->>ADK: Integrates worker result ADK-->>U: Final response

Code walkthrough

Step 1 RemoteA2aAgent Integration agents/coordinator/agent.py 
from google.adk.agents.remote_a2a_agent import RemoteA2aAgent

worker_a2a_agent = RemoteA2aAgent(
    name="worker_a2a",
    agent_card=os.path.join(
        os.path.dirname(__file__),
        "../worker/agent.json"
    ),
    description="A remote worker agent capable of background tasks.",
)

root_agent = Agent(
    name="coordinator",
    model="gemini-2.5-flash",
    sub_agents=[worker_a2a_agent],
)
RemoteA2aAgent — This class allows ADK to treat any A2A-compliant remote agent exactly like a local tool or sub-agent, parsing its exposed Agent Card.
Agent Card (agent.json) — The worker agent publishes an Agent Card that defines its rpc_url, capabilities, and skills. The coordinator uses this to know how to call the worker.
sub_agents parameter — The A2A agent is passed to sub_agents rather than tools, allowing ADK to handle multi-turn delegation transparently.
Step 2 The Agent Card (Discovery & capabilities) agents/worker/agent.json 
{
  "name": "worker",
  "description": "A worker agent...",
  "supportedInterfaces": [
    {
      "url": "http://localhost:8001/a2a/worker",
      "protocolBinding": "JSONRPC",
      "protocolVersion": "1.0"
    }
  ],
  "skills": [
    {
      "id": "worker",
      "name": "model",
      "description": "...",
      "tags": ["llm"]
    }
  ]
}
Agent Card definition — Just like a digital business card, this JSON defines who the agent is, what it can do (its skills), and exactly where to find it (supportedInterfaces).
protocolBinding — A2A relies heavily on standard HTTP POST requests with JSONRPC 1.0 payload structures to send the instruction and parse the result. Streaming is done via Server-Sent Events (SSE).
Dynamic A2A routing — When you run adk api_server --a2a agents, ADK scans the folder for agent.json. If found, it parses the card and automatically maps the A2A endpoints at the specified url!
Step 3 Generating Agent Cards Automatically build_card.py (example script) 
import asyncio
from google.adk.a2a.utils.agent_card_builder import AgentCardBuilder
from google.protobuf.json_format import MessageToJson
from agents.worker.agent import root_agent

async def main():
    builder = AgentCardBuilder(
        agent=root_agent, 
        rpc_url="http://localhost:8001/a2a/worker"
    )
    card = await builder.build()
    with open("agents/worker/agent.json", "w") as f:
        f.write(MessageToJson(card))

if __name__ == "__main__":
    asyncio.run(main())
AgentCardBuilder — Instead of hand-coding the JSON, ADK provides a builder that statically analyzes your root_agent to extract its name, description, and sub-tools/skills.
Protobuf Under the Hood — The AgentCard model inside ADK A2A SDK is a Protobuf message, not a standard Pydantic model. That's why we use MessageToJson(card) to serialize it perfectly.
Step 4 Under the hood: The JSON-RPC request HTTP POST Payload 
{
  "jsonrpc": "2.0",
  "method": "execute",
  "params": {
    "agent_id": "worker",
    "task": "Please analyze this dataset...",
    "context_id": "session-12345",
    "stream": true
  },
  "id": "req-8f92-4b2a"
}
Standardized envelope — Rather than ad-hoc REST schemas, A2A encapsulates every interaction as a JSON-RPC 2.0 call to the execute method.
Context propagation — context_id enables agents to remember state across multiple interactions in a single overarching session without sending full chat history every time.
Streaming support — If stream: true is passed, the worker will respond with text/event-stream (Server-Sent Events), allowing the coordinator to receive tokens in real-time.

FallbackLlm — How It Works

Used by hello_world, dota_draft_analyzer, and note_taking_agent. Lives in shared/utils/fallback_model.py and subclasses ADK's BaseLlm.

graph TD A["generate_content_async()"] --> B["Try primary\ngemini-2.5-flash"] B -->|Success| C["yield LlmResponse"] B -->|"429 / RateLimitError\nAPIConnectionError"| D["_should_fallback() True"] D --> E["Print warning to stderr"] E --> F["Try fallback\nollama_chat/qwen2.5:7b"] F --> G["yield LlmResponse"] B -->|Other errors| H["re-raise"]
Core generate_content_async — try primary, catch rate limits, route to fallback shared/utils/fallback_model.py 
class FallbackLlm(BaseLlm):
    primary_model_name: str
    fallback_model_name: str

    async def generate_content_async(
        self,
        llm_request: LlmRequest,
        stream: bool = False,
    ) -> AsyncGenerator[LlmResponse, None]:
        primary = self._get_primary()
        try:
            async for response in \
              primary.generate_content_async(
                llm_request, stream=stream):
                yield response
        except Exception as e:
            if self._should_fallback(e):
                print(f"switching to fallback",
                      file=sys.stderr)
                fallback = self._get_fallback()
                async for response in \
                  fallback.generate_content_async(
                    llm_request, stream=stream):
                    yield response
            else:
                raise  # non-rate-limit errors bubble up
async generator — matches ADK's streaming interface exactly. Works for both streaming and non-streaming without branching.
_should_fallback() checks for: ResourceExhausted, RateLimitError, APIConnectionError plus string matching on “429”, “rate limit”, “quota”, “resource exhausted”.
Silent to the user — warning goes to stderr only. The conversation continues uninterrupted; the user never sees the switch happen.
re-raise on other errors — auth failures, bad JSON, etc. should surface to the developer. Only rate-limit / availability issues silently fallback.
